# T4.9 — Cash reconciliation queue: outage runbook

The screen this task ships is **the reason Phase 4 exists**, so its T0
rollback — `owner.cash` off — is treated as an **outage**, not a rollback.
While it is dark (or broken), the owner falls back to reading the queue
view directly over psql. This file is that fallback, written as part of
T4.9 (`PHASE-4-OWNER.md` T4.9, "If it fails").

## The fallback query

`v_cash_reconciliation_queue` is the view the queue endpoint reads
(§10, `PLAN-DATA-MODEL.md` §4). Run against production — on athena:

```bash
psql "$SERVGRID_DATABASE_URL" -c "
SELECT e.full_name          AS employee,
       e.role,
       q.business_date,
       q.expected_cash::text,
       q.declared_amount::text,
       q.variance::text,
       q.flag
FROM v_cash_reconciliation_queue q
JOIN employees e ON e.id = q.employee_id
WHERE q.business_date BETWEEN (business_date(now()) - 14)
                          AND (business_date(now()) - 1)  -- default ends YESTERDAY
ORDER BY (q.flag = 'missing_submission') DESC,  -- the row the feature exists for, first
         q.business_date DESC,
         q.employee_name ASC;"
```

- **Default range ends yesterday**, exactly like the endpoint: add
  `AND q.business_date = business_date(now())` (or raise the upper
  bound) when today's picture is wanted, and read today's flags with the
  caption in mind — *“Today — still syncing. Figures settle overnight.”*
  A declaration that synced after midnight shows `no_expected_cash`
  until the day drains.
- **To focus one flag:** `AND q.flag = 'missing_submission'` (or
  `variance`, `no_expected_cash`, `match`).
- **To see the day behind an expected figure** (what the screen's
  *View the day* shows — the completions and cash payments that make the
  number):

```sql
-- completions (cash only — UPI/card never passed through anyone's hands)
SELECT j.job_number, c.name AS customer, jc.work_summary,
       jc.amount_collected::text, jc.completed_at
FROM job_completions jc
JOIN job_cards j ON j.id = jc.job_card_id
JOIN customers c ON c.id = j.customer_id
WHERE jc.completed_by = :employee_id
  AND jc.business_date = :business_date
  AND jc.collection_mode = 'cash'
ORDER BY jc.completed_at;

-- collected cash payments (the rep side, §10)
SELECT p.payment_number, co.name AS company, p.amount::text, p.received_at
FROM payments p
JOIN companies co ON co.id = p.company_id
WHERE p.received_by = :employee_id
  AND p.business_date = :business_date
  AND p.mode = 'cash' AND p.status = 'collected'
ORDER BY p.received_at;
```

The two lists' sums are the row's `expected_cash`. Confirm, dispute and
reopen are NOT safe from raw psql — they write `cash_reconciliations`
plus audit rows in one transaction (`apps/api/src/modules/cash/`); while
the API is healthy, drive the actions through
`POST /v1/cash/handovers/:id/confirm|dispute|reopen`, not by hand.

## When the flag is dark for one owner

`owner.cash` is evaluated per employee from `employee_flag_overrides`.
To light the surface for the owner while the investigation runs:

```sql
INSERT INTO employee_flag_overrides (employee_id, flag, enabled)
VALUES (:owner_employee_id, 'owner.cash', true)
ON CONFLICT (employee_id, flag) DO UPDATE SET enabled = true;
```

The queue and its three actions re-answer on the next `GET /v1/auth/me`
— no redeploy, no restart.
