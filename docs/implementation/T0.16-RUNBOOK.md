# T0.16 — Environments, backups, alerting (runbook)

The enablement is in the repo; this runbook is the sequence to prove
it on the VPS. The restore roundtrip, the bucket guard and the image
itself are already exercised on athena (§7 lists what was run); what
remains here needs hardware this repo does not hold — the VPS, the
off-site store, and two phone numbers. Owner actions are marked
**[owner]**; everything else runs from a shell.

## 0. What this run shipped

- `apps/api/Dockerfile` (+ root `.dockerignore`) — the API image CI
  builds and pushes to GHCR on every merge to main. Verified on athena:
  builds, boots, `/healthz` returns 200 with db and storage green
  behind caddy.
- `ops/` — the one-VPS stack: base `compose.yaml` +
  `compose.staging.yml` / `compose.production.yml` overrides, the ops
  `Caddyfile` (TLS for `SERVGRID_DOMAIN`), env templates
  (`ops/env.*.example`) and `ops/README.md`.
- `ops/backup/` — `backup.sh` (nightly `pg_dump -Fc`, integrity check,
  off-site ship, prune, dead-man ping), `verify-restore.sh` (restore
  into a scratch database **and query it**), `wal-sync.sh` (WAL
  segments off-site), `provision-minio.sh` (buckets, dedicated API
  user, bucket replication). Systemd timers in `ops/systemd/`.
- `seed/` — `001_owner.sql` (psql-variable protocol, hash from
  `apps/api/tools/hash-password.ts`), `002_services.sql`,
  `003_products.sql`. All idempotent, all run against a real migrated
  database on athena.
- Boot guard in `apps/api/src/config.ts`: `S3_BUCKET_EXPECTED` pins the
  bucket per environment; a mismatch refuses boot naming both values.
  Covered by `config.test.ts`.
- CI: `deploy-staging` builds/pushes `ghcr.io/<repo>/api` on every
  merge to main and ssh-deploys staging via `ops/deploy-staging.sh`
  once the `STAGING_SSH_*` secrets exist.

## 1. [owner] VPS and domain

1. Provision the VPS (any Ubuntu 24.04 box, 2 vCPU / 4 GB is ample) and
   a domain name. DNS: `staging.<domain>` and `api.<domain>` → the VPS.
2. Install Docker + Compose and the MinIO client:
   `apt install docker.io docker-compose-v2`, `mc` per MinIO's install
   page (into `/usr/local/bin`).
3. Set the timezone so the timers read naturally:
   `timedatectl set-timezone Asia/Kolkata`.
4. Create the layout and clone:
   ```bash
   mkdir -p /srv/servgrid/{staging,production,backups}
   git clone git@github.com:Yalt8826/ServGrid.git /srv/servgrid/app
   ```
5. A keypair for CI deploys: generate, put the public key in the VPS
   `authorized_keys`, and set the private key + host + user as the
   GitHub `staging` environment secrets `STAGING_SSH_KEY` /
   `STAGING_SSH_HOST` / `STAGING_SSH_USER`. Until then CI pushes the
   image and skips the ssh half.

## 2. Staging first boot

The env file lives **outside the repo checkout** so a deploy's
`git reset --hard` can never touch secrets:

```bash
cp ops/env.staging.example /srv/servgrid/staging/.env   # then fill every <>
```

Every `<>` gets a value; generate secrets with `openssl rand -hex 32`
(`-hex 24` for DB/MinIO passwords). The file is the T0.16 secrets
checklist in order: `JWT_SECRET`, S3 credentials, `FCM_SERVICE_ACCOUNT`
(path to `/etc/servgrid/fcm-service-account.json` from the T0.15
runbook), TLS via `SERVGRID_DOMAIN` + Caddy. Everything below uses one
helper — define it in the shell first:

```bash
dc() { docker compose --env-file /srv/servgrid/staging/.env \
  --project-directory /srv/servgrid/app/ops \
  -f /srv/servgrid/app/ops/compose.yaml \
  -f /srv/servgrid/app/ops/compose.staging.yml \
  -p servgrid-staging "$@"; }

dc up -d db minio
dc exec db chown postgres:postgres /wal-archive   # one-time; bind mounts start root-owned
dc up -d
```

Migrations are a release step, not a boot side effect:

```bash
dc run --rm api ./node_modules/.bin/tsx src/db/migrate-cli.ts
```

Seeds (staging = all three; psql reads the file on stdin):

```bash
HASH=$(openssl rand -base64 18 | pnpm -F api exec tsx tools/hash-password.ts)  # on athena

dc exec -T db psql -U servgrid -d servgrid_staging -v ON_ERROR_STOP=1 \
  -v owner_username=owner -v owner_password_hash="$HASH" \
  -v owner_full_name='<name>' -f - < /srv/servgrid/app/seed/001_owner.sql
dc exec -T db psql -U servgrid -d servgrid_staging -f - < /srv/servgrid/app/seed/002_services.sql
dc exec -T db psql -U servgrid -d servgrid_staging -f - < /srv/servgrid/app/seed/003_products.sql
```

Each seed prints the rows it ended with — read them. When
`fixtures/demo.sql` lands (PLAN-DATA-MODEL §8) it is the staging data
source; production data never is.

Then `https://staging.<domain>/healthz` → `200 {"status":"ok",...}` —
Caddy has obtained the TLS certificate by then (watch `dc logs caddy`).

## 3. Production, second

Same sequence with `compose.production.yml`, `/srv/servgrid/production/.env`,
`POSTGRES_DB=servgrid`, `S3_BUCKET=servgrid-attachments`, seed **001
and 002 only** (`003_products` is demo data; the real price list
enters through the API), and `API_IMAGE` pinned to a digest. Deploy to
production is manual, never a side effect of a merge.

## 4. Backups and the off-site store

1. **[owner]** Choose the off-site object store (any S3-compatible:
   Backblaze B2, Scaleway, Hetzner Object Storage…) and create two
   buckets per environment: the backups bucket
   (`OFFSITE_BUCKET`) and the attachments-replica bucket
   (`OFFSITE_ATTACHMENTS_BUCKET`). Keys go into ops/.env.
2. `ENV_FILE=... ops/backup/provision-minio.sh` — attachment bucket,
   dedicated API user (the `S3_ACCESS_KEY_ID` pair, scoped to the one
   bucket — never the MinIO root), replication wiring.
3. Install and start the timers:
   ```bash
   cp ops/systemd/servgrid-*@.{service,timer} /etc/systemd/system/
   systemctl daemon-reload
   systemctl enable --now servgrid-backup@staging.timer \
     servgrid-wal-sync@staging.timer servgrid-verify-restore@staging.timer
   ```
   (`@production` after §3.) Backup 01:30, WAL sync every 5 minutes,
   restore rehearsal first Saturday 03:00.
4. **[owner]** Set `BACKUP_PING_URL` to a dead-man monitor on the same
   uptime service as §6 — a backup that silently stops running must be
   as loud as an API that goes down. Run `ops/backup/backup.sh` once by
   hand and tick the ping.

## 5. Verified restore — the box that matters

An untested backup is a belief. On the VPS, after the first real
backup:

```bash
ENV_FILE=/srv/servgrid/staging/.env ops/backup/verify-restore.sh
```

Expected (the numbers come from the restored database, not the dump):

```
verify-restore: ok — applied migrations = 5 (>= 5)
verify-restore: ok — employees (the owner exists) = 1 (>= 1)
verify-restore: ok — service catalogue rows = 5 (>= 5)
verify-restore: PASS — ... restored into servgrid_staging_restore_check, queried, dropped
```

A failure keeps the scratch database and prints how to inspect it.
This was run on athena first (§7); on the VPS it is the same script
against the live backup pipeline — tick the box only when it printed
PASS from a dump the nightly timer produced.

## 6. Uptime checker — the entire alerting story

`/healthz` polled every five minutes by an EXTERNAL checker (external
so a dead VPS still gets noticed), alerting the developer and the
owner **by phone**. That plus the Phase 5 `tracking-health-sweep` is
all of it — no metrics stack, no on-call rota. Named destination so
Phase 5 finds no gap to over-build:

1. **[owner]** Create a **UptimeRobot** account (Pro plan — voice-call
   alerting, the cheapest path that actually rings a phone) and add
   two alert contacts: the developer's phone and the owner's phone.
2. Monitor: type HTTPS, `https://staging.<domain>/healthz`, interval
   **5 minutes**, timeout 30s, alert after 1 failed attempt. (Second
   monitor for `api.<domain>` once production exists.)
3. The proof, from the VPS (the `dc()` helper from §2): `dc stop api`,
   and **both phones ring within the interval + retry budget**
   (≤ ~6 minutes). `dc start api`; recovery notifications arrive.
   Record both numbers ringing in the issue — one phone is not the
   test, the owner's is.

## 7. What athena already proved (no VPS needed)

- `pg_dump` → `pg_restore` into a scratch database → queried: the
  exact `ops/backup/backup.sh` + `verify-restore.sh` pair, against a
  migrated + seeded Postgres 16 container, PASS with the counts above.
- The bucket guard: booting the image with `S3_BUCKET` ≠
  `S3_BUCKET_EXPECTED` exits at boot with
  `S3_BUCKET is '<other>' … refusing to boot`; matching/unset boots.
  (`config.test.ts` holds the table-tested version.)
- The image: build, boot against db+minio, `/healthz` 200 via caddy.
- Full suite: typecheck, lint (three custom rules), unit + integration
  against real Postgres, migration up → down → up.
